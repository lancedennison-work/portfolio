Loop Factory*

* temporary name

A text-based incremental factory game where players manage a factory through a terminal-style Control Panel — writing configs, collecting resources, discovering map sectors, and unlocking new blueprints over time.

Though I work on this game almost every day — with much of it being pure code, I won't have daily updates to showcase my progress.

Phase 1: Foundation

step 1

Getting Started

The Pitch

image — sketch of the UI

The game is a terminal-driven factory simulation inspired by cassette-futurist aesthetics. The player takes on the role as the sole remote operator of an industrial facility— constructing production lines, designing custom machines, and balancing limited factory resources to automate an increasingly demanding manufacturing process.

Preliminary Assessment

The main challenge with this idea is game feel. Without a visual factory space, the moment-to-moment satisfaction of organizing and optimizing a system is less immediately rewarding than traditional factory sims. The terminal interface and manual machine configuration introduce significantly more friction than visual builders. This creates a design risk: if the learning curve is too steep, progression may not reach a point where the player feels meaningful payoff.

Because of this, onboarding becomes a critical part of the experience. The early game needs to introduce systems gradually while still making the player feel in control of the factory. The tutorial layer will likely require as much iteration as the underlying mechanics.

That said, I don't expect the lack of visuals to reduce engagement on its own. Games like Shapez show that minimal visuals can still support strong factory simulation gameplay, and Factorio demonstrates that clarity of systems matters a lot more than graphical fidelity. The goal here is to lean into a cassette-futurist computing fantasy, using terminal presentation and CRT-inspired styling to reinforce the feeling of operating a remote industrial system in an alternate future.

To sustain engagement over time, the player needs constant forward momentum. "Numbers go up" works as short-term feedback, but isn't enough on its own to keep someone playing through to the end. The game needs a steady stream of goals — new materials, unlocks, and system upgrades — that give the player something concrete to pursue at all times. These need to be paced carefully: frequent enough to maintain interest, but not so dense that they overwhelm the player with new systems before they feel like meaningful advancement.

Design Philosophy

Before building any systems, I wanted to establish a few guiding principles for the project to help ground design decisions as development continues.

Ludological Story: Remote Operator. The core fantasy is simple: the player is the sole operator of a remote industrial facility. Rather than physically walking through a factory or placing objects in a 2D world, every interaction is performed through a terminal. The player isn't controlling a character — they're in an office managing a system. The setting is still being developed, but the feeling draws heavily from cassette-futurist media like Alien, where terminals are functional, tactile, and retro.

Immersion Without Friction. A realistic terminal expects the user to memorize commands and navigate text menus without shortcuts. While that supports the fantasy, it can also become frustrating if the interface gets in the way of playing the game. Whenever those two goals conflict, gameplay takes priority over aesthetic.

Grounded, Not Simulated. The production chain takes inspiration from real industrial processes, but accuracy is never the end goal. Real industrial processes are often too slow or complex to make interesting gameplay. Realism serves as a foundation for progression and machine design, while gameplay determines where abstraction is appropriate.

Optimization as the Gameplay Loop. Factory space and processing capacity are intentionally limited, encouraging the player to think carefully about which machines deserve space and what production chains are current priorities. The objective isn't to build the biggest factory possible — it's to build the most effective one with the resources available.

Finding the Right Engine

Games like Satisfactory, Mindustry, and Autonauts are key inspirations, even though they rely heavily on visual simulation. This project compresses that same factory-building fantasy into a terminal-based UI rather than a spatial environment. That immediately raises a practical question: what engine is actually suited to this game?

Unity and Unreal are the obvious portfolio choices. Unity's UI Toolkit has come a long way, and Unreal's UMG can handle complex interfaces. But realistically, both engines are built around rendering pipelines, physics, and 3D scenes. Stripping all of that out to build what is essentially a stylized text application would mean fighting the engine more than using it.

Godot fits the project more directly. Its scene system is lightweight, its Control node framework is built for UI-heavy layouts, and its built-in TextEdit and CodeEdit nodes support terminal-style interaction naturally. More importantly, it starts from a very minimal baseline — meaning unnecessary systems don't need to be removed or worked around.

step 2

Building the UI Foundation

First Impressions of Godot

Godot was a genuine surprise. The portability alone stood out immediately — no installation friction, performs well on lower-end hardware (including my 8GB RAM (!!!) Surface Pro), and doesn't feel stripped down in capability. Their documentation is thorough and well hyperlinked, making it easy to navigate unfamiliar classes and methods. The one real gripe I have is that methods are documented but rarely shown in context, which means a lot of trial and error to understand how things actually behave at runtime rather than just what they theoretically do.

Wrangling the Panel Layout

With six planned panels — Edit, Control, Map, Info, Space*, and Resource — the first task was getting them all sized, positioned, and styled consistently. The design goal was a white rounded-corner outline that turns green when a panel is active. On paper, this is straightforward. In practice, each node type behaves differently when it comes to styling: PanelContainer doesn't handle StyleBox overrides the same way CodeEdit and TextEdit do. Getting a consistent border effect across node types, each with their own rules about how styles are applied, took manual spoofing of theme behaviors that should have been uniform.

The other small headache was focus management. Clicking off a panel needed to properly clear the active state, but there was no clean way to catch an unfocused click on empty space. The fix was placing a full-screen Button at the back of the scene to absorb any click that didn't land on a panel, forcing a focus reset.

step 3

The Map Matrix

Function vs. Form

The map is organized as a 4x9 matrix covering locations A1 through D9. My initial instinct was to index the matrix starting at 0, since matching the internal array indices to the displayed coordinates would be more natural. Despite that, I found the 1-based layout significantly more readable from the player's perspective. There wasn't a technical reason for the decision — it just looks better. The alternative is to keep the underlying coordinate system separate from what the player sees.

gif — map grid with tooltips

update

After experimenting with both approaches, I ultimately decided to remove vector coordinates from the player's end entirely. All player interaction now uses the A1–D9 matrix notation, leaving the vector representation as an internal implementation detail.

Column-First Meets Row-First

The first attempt built the matrix and buttons in a single loop iterating column-first, which is the natural way to think about a 2D array. The problem is that GridContainer fills left-to-right row by row, so the buttons end up visually arranged as columns rather than rows — correctly indexed in code, totally wrong layout in UI.

Rather than forcing the UI to conform to the data structure, I separated the two concerns. The matrix is still populated column-first, but the buttons are added in row-major order to match the visual layout. Alongside the matrix I built _button_directory, a flat label-to-coordinate dictionary, so button lookups don't require scanning the full array every time.

Making Location Inputs Flexible

The more interesting challenge was find_cell.

One of my design goals is to avoid frustrating the player over something as simple as typing style. Whether someone naturally enters [A1], bare A1, a casual a1, or even (0,0), the game should understand what they mean whenever possible.

Rather than handling each format separately at every call site, I consolidated everything into one function using two regex patterns. The coordinate format is checked first since it's syntactically distinct, and the function returns both the resolved Vector2i and label string together so callers never need a second lookup. As a result, any system that references a map location automatically inherits support for every accepted input format without additional implementation.

step 4

The Terminal and File System

Spoofing the Terminal

The Control Panel serves as the player's primary interface with the factory, so making it feel like a real terminal was one of the first priorities. The goal was to make a CodeEdit node behave like an actual command-line interface, which turned out to require much more intervention than expected. Terminals have a lot of subtle behavioral rules that users take for granted: the caret can't move behind the prompt, clicking doesn't reposition the caret, UP and DOWN scroll through history rather than moving between lines. None of that exists by default in CodeEdit, so each behavior had to be explicitly intercepted and handled.

The history system, command extraction, and input guards all came together quickly enough, but the bigger realization was that complex operations were going to need a way to ask the player follow-up questions mid-command.

gif — terminal manipulation

Letting the Terminal Request Information

The solution was get_player_input, a function that lets any part of the codebase pause, ask the player something, validate the answer, and resume — without any of that logic pre-existing inside the terminal itself. The caller passes a message, an expected type, a callback, and an optional validator. The terminal switches into AWAITING_CUSTOM_INPUT state, handles all the prompting and re-prompting, then calls the callback with the validated result and emits input_received. Anything that needs to chain multiple questions just pauses for the await signal between calls.

update

This turned out to be one of the more important architectural decisions in the project. Machines use it to ask for missing configuration at startup, the file system uses it to confirm creation and deletion, etc. Without it, all of that would have had to live inside the command handlers rather than in the systems that actually need the information.

A Confusing Engine Limitation

With the terminal functional, the next task was the file system. CodeEdit inside EditPanel handles all file manipulation since it's the node the player directly edits in. Getting syntax highlighting working was the first real fight. Godot exposes a method to retrieve the theme their own editor uses, which would have been perfect — but it isn't callable at runtime. A built-in coding node that can't access the coding theme of the environment it lives in is a baffling decision, but it just meant setting every color up manually by cross-referencing Godot's editor theme values. More tedious than difficult, but the kind of thing that costs time for no satisfying reason.

screenshot — syntax highlighted code in EditPanel (left) vs Godot editor (right)

After that, the file commands themselves came together quickly: load, save, close, create, and delete all wired into the terminal. The EditPanel was also updated at this point — rather than showing a placeholder message when no file is open, it now lists the contents of the custom machines folder, so the panel is always showing something useful.

step 5

Items, Inventories, and Materials

Building the Inventory Handler

Before machines could do anything meaningful, the game needed a solid foundation for moving items around. The design goal was a system flexible enough to be shared across machines, the Vault, and transport ports without needing to be rewritten for each context.

The core Inventory class handles basic add, remove, and query operations. A key concern is avoiding silent failure states where a machine appears to do nothing due to missing configuration. To support more flexible behavior, two additional functions are added: take_max, which drains as much of a resource as available instead of an exact amount, and get_max, which retrieves the most abundant item in an inventory. Both will be important later for flexible refining behavior, and hopefully avoid that high-friction situation that bothers me in other sims.

Rethinking the Port System

The port system went through one significant design revision. The initial plan was for InputPort and OutputPort to act purely as reference links — each port pointing to its own machine and whatever it was connected to, with the machines themselves handling transfers. The problem with that approach is that machines can have many ports with varying desired behaviors, and centralizing transfer logic on the machine would mean a lot of conditional branching for what should be a uniform operation.

Moving the transfer logic into the ports themselves made each port independently responsible for its own behavior, which is a much cleaner separation. InputPort has a pull() function specifically for pulling from the Vault, since giving the Vault a unique OutputPort for every connected machine would be unnecessary overhead. I created a PortResult that wraps the return so failures report cleanly without crashing.

Setting Up the Vault

Getting the display layout right took the most iteration of anything so far. A plain scrolling list fell apart quickly as the number of resource types grew, so the final solution was a scrollable HFlowContainer that wraps items into columns naturally. The scrollbar styling still needs work — after far too much fighting with StyleBox, that one got left for later.

One Place for All Materials

All material definitions are centralized in materials.gd, which acts as the single source of reference for every material type in the game — ores, raw materials, alloys, synthesized compounds, vaporized gases, and eventually manufactured products. Machines do not hardcode material behavior; they query this shared database and operate based on the returned data. Adding a new material type or processing method means changing one file, not hunting through machine scripts.

step 6

Constructing Machines

The Machine Blueprint

With inventories and materials in place, the next step was the machines themselves. The Machine base class is the foundation everything else builds on — it owns the inventory, the input and output ports, the process queue, and the construction requirements. Since the custom machines might have multiple internal machines, I want each loop of the factory to only perform one step at a time. The base class' operate() works through a queue of callables one loop at a time, which means complexity naturally scales with how many processes a machine has registered.

Rethinking Errors

As machines become more complex, machine errors equally increase in complexity. In a visual factory game, players can often visually troubleshoot an issue in production. In a text-based factory, they need feedback provided explicitly. This led to three separate logging systems: Factory Logs for management operations, Machine Logs for machines' internal activities, and Error Logs for failures. The goal is to make the factory understandable without forcing players to hunt for why something did or did not happen.

However, I realized that Machine.Error no longer fit my needs alone — I need to be able to display the factory's functioning separately from the errors encountered. So I added success codes to the enum definition so that, for example, when a machine is constructed successfully, the code reads as a success and is given to the operation log rather than the error log.

The Scene Tree is Out to Get Me

This is where things got bumpy. Machines need to check the Vault for construction requirements during construct(), which means accessing resource_panel, a node reference that must be resolved at runtime via @onready. The problem is that @onready variables don't populate until a node is inside the scene tree — and I need to call construct() before add_child(). Every node reference on the machine was null, producing silent failures that were initially very confusing to track down.

The fix was enforcing a strict operation order in machine_manager.gd: instantiate the machine, give it the information it requires, add it to the scene tree first, then call construct(), then call setup(). Making the ordering explicit and consistent across all machine construction paths meant that each step accessed only the data it was ready for.

Preparing for the Future

After setting up the first two specialist classes, I realized that there are multiple machines that might use the same behavior as smeltingFurnace and I could set up a class to streamline later class definitions. refiningMachine serves as a base class for anything that transforms one material into another in a single step. Rather than hardcoding smelting logic into the furnace, refine() takes a process method name and output port, queries Materials for whether the current input can be processed that way, applies the efficiency multiplier, and handles the output. Adding a new type of refining machine later means extending refiningMachine and calling refine() with a different method string — the materials database handles the rest.

The Construction System

With machines proven to work, the construction system needed to give the player a way to build them through the terminal. The construct command kicks off a multi-step flow: type, level, name, and optionally a location for expedition machines. Each step is handled by _collect_construction_data, which advances through a CON_STEP enum and re-prompts for the current step if the player's input doesn't satisfy it.

This layered approach maintains my stance on prompt flexibility. I don't want everything to fall apart if the player left out one piece of the required arguments — it handles what it was given and continues until it has all required information.

gif — construct command walking through steps

Handling Every Outcome

The back end of construction is _continue_construction, which calls machine_manager.add_machine() and routes every possible ConstructionHelper.ERROR result to an appropriate response. Success cases start the machine immediately. Recoverable errors — name already in use, location occupied, insufficient resources — either re-prompt for a different value or drop back to IDLE with an explanation. The goal was that no outcome leaves the player without feedback or stuck in a broken state.

step 7

Making Custom Machines Custom

The Design Goal

screenshot — custom machine config file in EditPanel

The entire point of the Edit Panel is letting players define their own machines — as a way for players to construct tailored production systems that reflect their own approach. The core design challenge is determining the appropriate level of control: players should be able to define production behavior and structure machine relationships, but also need to be restricted from accessing machine variables to make infinite item generators.

A Major Road-Block and Pivot

The original direction assumed players would eventually be able to define machine behavior through code definitions inside the EditPanel. However, this plan breaks down at implementation due to Godot's runtime constraints. The engine does not support compiling or loading new script definitions during runtime in a way that would allow true programming. Supporting that would require building a system to completely mimic GDScript's compiler, which grossly exceeds the scope of this project.

More importantly, this limitation exposes a deeper design issue: the assumption that runtime scripting would meaningfully improve the gameplay experience. Loop Factory* is not a simulation of agents executing programmed instructions in a world. There are no autonomous actors to script, or physical systems requiring behavioral programming.

Config-Driven Construction

This shifts the game toward configuration-based machine definition. Instead of defining behavior through code execution, players define structure through systematic configuration. A custom machine is built from a config that specifies sub-machines, inventories, and port connections. This preserves meaningful player agency while keeping all behavior grounded in existing, well-defined machine systems. The complexity emerges from how systems are composed, not from the minutia of code.

The same scene tree ordering problem from before applied here too — sub-machines have to be added to the scene before their ports get assigned, otherwise the @onready references fail in exactly the same way. The construction sequence for a custom machine mirrors the base machine pattern but nested: add parent, construct parent, then for each sub-machine add it, construct it, call setup, assign connections.

Adding a New Blueprint

Once custom machines are reduced to configuration definitions, the final step is integrating them into the existing construction process. A command add_custom_machine in code_edit.gd loads the script file, reads its config dictionary directly off the class, and hands it to machine_manager. With this, the player can write a config, run add [filename], and the machine appears in the construction list — ready to be built with the construct command.

Phase 2: Functional Content

step 1

Filling the Foundation

Shifting Focus

Phase 1 establishes the systems the game is built on: machines, inventories, materials, terminal interaction, and custom machine definitions. With those foundations in place, the focus now shifts from building gameplay systems in isolation to making them work together. This phase is about turning those building blocks into an actual game — expanding the roster of blueprint machines, completing the Control Panel's functionality, introducing progression systems, and refining the gameplay design.

The Factory Loop

The core limitation of the factory is not keeping a sprawling factory organized — it is processing capacity. Every machine occupies one of a limited number of factory slots, and every factory loop represents a shared processing budget. Each loop gives every machine an opportunity to perform a scaling unit of work before the factory advances to the next cycle.

This creates a constant tradeoff between specialization and consolidation. Simple blueprint machines only perform one process, but they complete that process in a single call. Custom machines can combine multiple production steps into one machine — increasing the number of machines the factory can host, but requiring additional processing loops to complete their internal sequence of operations.

Since factory space is limited, players are continually deciding whether they want a slow but complete and passive chain, or fast production speeds that have machines being quickly swapped in and out of the Loop.

Example Progression

Progression grows naturally from this loop. Processing new materials unlocks additional production methods, which in turn unlock new blueprint machines capable of handling them. A player might begin by refining ore with only a few specialized machines connected together. Later, after unlocking additional processing methods, those same production steps can be combined into a single custom machine that occupies one factory slot instead of several. The goal is not to replace earlier machines, but to continually present better optimization opportunities or the production of new materials.

step 2

More Machines

Expanding the Processing Chain

With the foundational machine systems working, the next priority is expanding the set of blueprint machines available to the player. Up to this point, the factory is only capable of a simple, one-step refinement. Rather than treating every new blueprint as a unique machine, I began grouping them by the kind of work they perform. Refining machines remain responsible for transmuting a single material, while a new family of separation machines breaks a single resource into multiple outputs.

After creating the second refiningMachine variant, industrialOven, I implemented the separatingMachine parent class. This machine handles any [method]_separation() process by taking a raw input and using the corresponding method in the Materials lookup to convert it into separated components. It then routes outputs either through designated output slots or automatically assigns them to unspecified material outputs. Once the parent class was complete, setting up its children was straightforward: electricalSeparator, chemicalSeparator, mechanicalSeparator, and thermalSeparator.

Emerging Issues

The first separation machines reveal a problem that the refining machines never had to solve. Refinement always produces a single destination, but separation generates several different materials at once. If the player doesn't explicitly assign every output, the machine still needs to distribute its products instead of stopping or requiring additional configuration.

This led me to rethink how machine outputs work. Rather than assuming every produced material already has a dedicated destination, machines now assign outputs dynamically to compatible connections as resources change. Besides reducing unnecessary player interaction, this makes the entire processing system far more flexible. Future machines can produce increasingly complex combinations of materials without requiring custom output logic for every new blueprint.

Introducing Combination Machines

The last major machine category for this milestone handles the opposite problem. Instead of transforming or splitting a single material, these machines combine multiple ingredients into a new product. This introduces recipe-based production, allowing factory chains to converge as lower-tier materials are assembled into more advanced resources.

I named this class recipeMachine, which operates by setting a recipe target, populating its queue_inventory with required amounts, consuming the inventory, then adding the refined product to output_inventory for distribution. Currently it is used by metallurgicFurnace for alloy production and chemicalReactor for synthesized materials.

step 3

Comparative Analysis

Identifying Friction

One of the core design goals of Loop Factory is reducing unnecessary friction without reducing meaningful decision-making. To help evaluate that balance, I started looking more closely at other factory games to identify interactions that feel more expensive than the decisions they ask the player to make.

Recently I've been playing Star Rupture, and one interaction in particular stood out. After building a processing machine, assigning its output material, and completing the logistics chain by connecting it to a new storage depot, the game still requires manually assigning the storage depot's material type — even though there is only one possible choice. Individually this feels like a minor inconvenience. Repeated across an entire factory, however, it becomes a significant source of friction. A line of ten identical setups means repeating an interaction that provides no new decision, only additional work.

Breaking the process into its individual actions makes the cost easier to see:

      • +/- Scroll to rail blueprint
      • Select rail blueprint

  • 3.5: Extend transport rail - T +2T actions

Ignoring movement entirely, this results in a minimum of 15 actions, with an upper bound of 30 + 3T actions for a single production chain. Replicating that setup ten times can easily require hundreds of interactions, despite very few meaningful decisions being made.

update

While writing this, I realized why this interaction rarely bothers me in games like Mindustry. The difference isn't just the interface — it's the dimensions the player operates in. In a 3D factory game, configuring machines often means physically traveling between them. Every menu interaction interrupts navigation, and when the menu closes the player must re-establish their position, orientation, and immediate objective. In a 2D game, the camera can pan directly to another machine without the same interruption.

This aligns well with Cognitive Load Theory. Closing a 2D menu in a 3D environment results in "Attentional Disengagement" and requires reconstructing three things: spatial context, motor mapping, and goal state (abstract). In a 2D environment, rebuilding that context is substantially easier. Personally, I would estimate that motor context and perspective changes in a 3D game increase the effective cognitive load by roughly 2-4 times compared to the same transition in a 2D game. This was covered in a textbook I had used, but I was unable to find the source

The important lesson for Loop Factory is that interactions should be automated or consolidated wherever possible. If there is only one logical outcome, asking the player to confirm it every time adds work without adding gameplay. One improvement I plan to explore is allowing machine configurations to infer obvious defaults from existing connections. For example, if one machine outputs raw_iron and the next connected machine is a smeltingFurnace, that machine should automatically select iron_bar as its processing target whenever no ambiguity exists.

step 4

Flexible Inventory

Comparing Inventory Layouts

As the machine system grew more capable, it became clear that the current inventory architecture no longer aligned with the flexibility goal. Rather than committing to another incremental change, I stepped back and explored several different inventory layouts to understand the tradeoffs each one introduced.

Option 1: The Current Design

jpeg — inventory diagram option: 1

The existing approach treats a custom machine as a single unit. Internal sub-machines do not own independent ports; instead, they share the parent machine's input and output inventories. This keeps the overall structure simple, but it also means every internal machine is tightly coupled to the parent. As more processing chains emerge, that coupling starts limiting how complex the internal systems can be.

Option 2: Simplicity First

jpeg — inventory diagram option: 2

This layout gives each sub-machine its own inventories while keeping routing largely managed by the parent machine. It is the least complicated design to understand and implement, and most factory layouts would work without much overhead. The drawback is flexibility — since the routing is effectively built into the structure, changing connections at runtime requires the parent to directly manipulate sub-machine inventories, which makes future customization more fragile.

Option 3: Everything Through Ports

jpeg — inventory diagram option: 3

This setup treats sub-machines much more like independent factory components by giving them their own ports and routing every transfer through those interfaces. It introduces slightly more structural complexity, but provides the greatest amount of runtime flexibility. Connections can be reconfigured without reaching directly into another machine's internals, and every transfer continues to use the same validation and safety rules as the rest of the factory. That consistency feels much easier to build upon.

Option 4: Disabusing Old Fixations

jpeg — inventory diagram option: 4

While exploring these layouts, I realized I had been holding onto an assumption from much earlier in development. I originally wanted custom machines to feel fundamentally different from simply taping several machines together, so I was attached to restricting sub-machines from connecting directly to the outside world. The more I experimented, though, the less convincing that reasoning became — the restriction isn't functionally different, it only introduces extra configuration work.
This option no longer forces internal machines into isolation: they can directly link ports to external machines but can still be referenced from the shell. The shell would no longer have its own inventories, and the internal machines would still use ports to interact with their siblings. I'm still not completely convinced the answer is simply removing the distinction altogether — I still think isolated sub-machines lend toward custom machines feeling different from stand-alone machines.

The Crunchy Stuff

Inventory System

The inventory architecture went through another major redesign. Earlier versions relied on machines owning large shared inventories, but that increasingly conflicted with the goal of making machines easy to reconfigure at runtime. Ports now own their own typed buffers — responsible for moving materials between machines — while machines keep only a dedicated _processing_inventory for work currently in progress. _inventory and _output_inventory are gone from Machine. A new flush() drains _processing_inventory into output port buffers via take_up_to.

Port System

The inventory redesign also exposed weaknesses in the original port architecture. Raw dictionaries for input and output have been promoted to typed InputSystem/OutputSystem classes. All port access routes through a safe _get_port() with context-aware error logging. Ports can now be protected against removal, renaming is atomic, and a new make_port_id() standardizes auto-generated naming. PortSystem holds a direct machine reference so flush() can access the processing inventory without awkward cross-object reaching.

Machine Lifecycle

As machines gained more features, their startup sequence also became more complicated. The setup → verify_requirements → start chain is now clearly defined: start() registers the process queue then calls verify; restart() skips registration and calls verify only. A _halt flag separates intentional stops from failed verification, so the user can stop a malfunctioning machine from trying to restart each loop to avoid stacking errors.

Recipe & Separator Port Reconciliation

Recipe-based machines and separator machines were solving the same problem independently: ensuring their ports matched their current processing requirements. Rather than maintaining multiple versions of nearly identical logic, I consolidated this behavior into a shared _reconcile_ports() helper called by both set_recipe and verify_requirements, breaking the mutual recursion the previous design had.

Control Panel

The Control Panel continues to grow into the central interface for managing the factory. input_received now carries an InputResult payload so callers can distinguish completion, cancellation, and halt. Prompt state is now an InputRequest class rather than a raw dictionary. halt is valid as a response to any machine prompt; a suppress system was added for per-machine and global output silencing, and cmd_cancel now correctly emits its signal to unblock waiting machine coroutines.

Custom Machines

The earlier inventory redesign naturally carried over into custom machines. Shared inventories between sub-machines are replaced by direct port-to-port linking. verify_requirements now runs sub-machines first before checking external ports. Config connections are validated at verify time rather than assumed correct, and sub-machine prompts are prefixed with the parent name for player context. The more I refine the architecture, the more valuable this consistency becomes — every redesign removes another special case, making custom machines behave less like exceptions and more like natural extensions of the factory itself.

Phase 3: Finalizing

Phase 4: Polishing
