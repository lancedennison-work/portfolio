AI movement

Enemy AI Locomotion (Manual)

To make AI pathfinding, without the actor using pre-calculated movement paths from the engine, they need a solution routing around to objects blocking their path.

wall bumpers

This solution prevents the agent from being colliding into walls by adding a buffer, essentially adding bumpers to obstacles.

This behavior is guided by the following loop

  1. Set the movement target to the player's last location.
  2. Draw a straight line to the target.
  3. Is there a collision?
    1. Get the location of the collision object's center
    2. Calculate the vector from that center to the collision location
    3. Increase the magnitude by a buffer amount
    4. Set the endpoint of that vector as the new target destination.
  4. Move towards the target.

This solution has major drawbacks— it is more expensive per-tick than a pre-calculated movement space, and it also creates a "wall-hugging" behavior. Instead of walking around obvious obstacles, they will first try to walk straight through the wall until they get within buffer range, then they begin to route around it.

endpoint avoidance

This solution, instead, investigates the farthest obstructive endpoint of the obstacle, then adds a buffer at that point.

To the left is a secondary option of this method; using the orthoginal vector starting from the original path vector.

This loop would be performed for both left and right of the collsion point and whichever is shorter wins.

  1. Set the movement target to the player's last location.
  2. Draw a straight line to the target.
  3. Is there a collision?
    1. Sweep query hit trace.
    2. Are we no longer hitting the obstacle?
      1. Use previous collision trace.
      2. Add a buffer vector orthoginal to that trace's vector.
      3. That location becomes new intermediate location.
  4. Move towards target.

This solution creates a different problem. This effectively sets multiple straight lines as the path, so they run in a straight line, perform a sharp turn, then run in a straight line again— very robotic.

how can fix?

If the agent, rotates then moves it creates the path shown in the solid black line.

But, if you have the agent rotate as they move, it creates a curved path. The tricky part is how fast they should rotate, so that they actually arrive at their location, and they don't go so wide they run into a different wall.

In the ideal scenario, that results in the dashed black line.

Reassess

Reframe

I have decided that manual sweeping through an object is too costly to perform, especially if the agent is going to have to avoid a lot of obstacles in one go.

Therefore, I am turning to BoxExtent. If I perform a dot product with the BoxExtent and the orthogonal AxisDir, we get the distance traced down the AxisDir to the edge of the BoxExtent.

const FVector Right = (FVector(0,0,1) ^ StraightPath).GetSafeNormal();

note

AxisDir = Right

const float EdgeDistance = FVector::DotProduct(ObjectBounds.BoxExtent, AxisDir.GetAbs()) + Buffer;

Is this a single check (as is times performed) to find the edge of the object rather than a bunch of different traces to slice through until it finds a clear shot.

This also has gained a few capabilities, if the new path— buffered from the edge— also hits something, it measures the distance between the two objects, and if there is room to walk down the midpoint, then it adds that as the intermediate location.

Good news: The pathfinding works!

Bad news: It doesn't.

It does correctly go around objects, but you might have noticed that something was off… This pathfinding only works because the buffer is set to much larger than realistic value.

In the gif, only the rectangle box is being avoided, the problem is that the 'wall' is a composite object. This problem is exacerbated by what I am calling the 'midpoint problem'; currently it traces out to the edge of the object to get the edge distance from the object origin, which means, if we are trying to go through a box, it puts the intermediate point off of the center of that wall, which is not what we want. This problem is demonstrated below.

This calculation is supposed to work the first time to avoid the single object, and right now, it doesn't.

What can we do?

There are two ways we can go about this: more probes, or grouping shapes into their composite.

Performing more probes keeps things aligned with my goal of doing things manually, but it quickly becomes an issue.

Which is solved with grouping. If the agent is trying to get somewhere that is straight through a wall that is composed of many blocks, the rechecking might need to go though 50 more blocks that reach all the way to the edge of the map. If you group together the objects you can use the whole shape.

But this has a problem, in the below scenario, both the Bounds.SphereRadius and the Bounds.BoxExtent would result in going wide around a completely empty space that would realistically be cut across. Robust(er) Pathfinding

note

This is by far the biggest addition to this project ~1000 lines.

I tried very hard to make this as robust as possible, and ran into some severe limitations in my engine knowledge.

Midpoint [not a] Problem

Before even working on the composite solution, the pathfinding needs to work on a single shape.

Here is what we now do when we hit an object.

  1. SetMovementTarget — TickPatrolling / TickInvestigating call SetMovementTarget to set off the cascade. Planning is collision-triggered— it is only used when the path ahead is obstructed.
  2. EvaluateNextMovementLeg — the main planning loop. It first checks whether an existing queued path is still clear, then loops up to MovementLegsAhead, probing and resolving one hop at a time.
    1. IsPathClear — swept box, agent-sized, along the leg. Returns true if clear. The sweep is lifted by MaxStepHeight. (Now they can use their legs to step over things!!!)
    2. FindPath — the core step for the avoidance loop. Derives Right/Left from the hit surface normal, builds the obstacle footprint, finds the relevant tangent corners, resolves both sides unconditionally, then picks a winner based on total distance.
      1. Obstacle footprint — the nearest single AggGeom element, flattened to XY and hulled.
      2. FindHullTangentVertices — finds the tangent corners as seen from the agent.
        1. A vertex is tangent when both hull neighbours fall on the same side of the view ray — two cross products.
        2. Not the hit face's corners: those only coincide with the tangents head-on, so once a corner is rounded one of them is behind you.
      3. TryResolveAvoidanceSide — resolves each side independently and validates the resulting candidate by re-sweeping.
        1. TryGetSphereTangentPoint — for round obstacles, computes the candidate in closed form.
          1. L = √(D² - R²); the touch point is P + (L²/D)·D̂ ± (L·R/D)·⊥. AxisDir's sign picks which of the two.
        2. ComputeBufferedCornerPoint — for cornered obstacles, offsets the tangent corner outward along the bisector of the two meeting faces.
          1. Distance is Buffer / cos(half-angle), which clears both faces by exactly Buffer at any corner angle.
          2. Guarded against extremely acute corners, where it approaches infinity.
        3. Candidate validation and buffer growth — TryResolveAvoidanceSide first rejects candidates within HopAcceptanceRadius as no-progress.
          1. Otherwise it re-sweeps the candidate.
          2. Same obstacle blocks -> double the buffer and retry for MaxBufferGrowthAttempts.
          3. Different obstacle -> dead end.
      4. Scoring — after both sides have been resolved, the shortest path wins.
        1. If MovementLegsAhead is insufficient to reach MovementTarget, then a winner is chosen by the naive distance from the last hop of the leg to MovementTarget.
    3. Failure — if FindPath cannot produce a valid route and no existing queue or newly generated hops remain, RegisterPlanFailure applies a cooldown to edge out moving obstacles.
      1. After MaxConsecutivePlanFailures, the target is abandoned.
      2. For patrolling, this results in skipping the attempt at reaching the current patrol point and advancing to the next.
  3. TickMovement — walks the resulting queue.
    1. Hops use a tighter acceptance radius than the destination — avoidance is more precise than arrival.
    2. When a hop is reached, it is popped and EvaluateNextMovementLeg runs again to refill the queue, continue straight, or give up.
