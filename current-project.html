Loop Factory*

* temporary name

A text-based incremental factory game where players manage a factory through a terminal-style Control Panel — writing configs, collecting resources, discovering map sectors, and unlocking new blueprints over time.

Phase 1: Foundation

step 1

Getting Started

The Pitch

Loop Factory is a text-based incremental factory game where the player manages a factory through a terminal-style "Control Panel." Starting with basic machines, players can write configurations for custom machines in the Edit Panel, collect resources, discover new map sectors, and unlock new blueprints and specialized function panels over time.

Preliminary Assessments

The main hurdle with this idea will be game feel. Without a visual component to the game, there is less satisfaction in the organization process of a factory manager game. The terminal interface and manual machine configuration are higher-friction than visual builders; this is a design risk if the learning curve out-paces progression before the player accomplishes enough to feel the payoff. Onboarding matters more here than in visual factory games due to the less intuitive gameplay, so I will have to pay significant attention to the tutorial.

However, I don't anticipate the lack of visuals to diminish appeal. Games like Shapez prove that stripping down visuals doesn't come at a cost; you don't need ultra-realistic graphics to engross a player in their factory sim (I mean look at Factorio). The goal with my game is to lean into the fantasy of retro-futurism computing; borrowing aesthetics from media and applying effects like a CRT filter will be doing a lot of heavy lifting.

To keep factory sims engaging, you need to constantly give the player something to work towards. "Numbers go up" holds a lot of appeal, but won't keep them playing. I need to ensure there is always a quest or unlock that the player is chasing, and pace them close enough together to maintain satisfaction without overwhelming the player with new features and notifications.

Finding the Right Engine

The satisfaction of watching a system you designed for brutal efficiency run on its own is something I wanted to capture, but stripped all the way down to text — literally just "numbers go up." Games like Satisfactory, Minedistry, and Autonauts are my biggest inspirations for this project, but they are all mostly visual based games. That immediately raised a question: what engine best fits a game that's entirely UI?

Unity and Unreal are the obvious portfolio choices. Unity's UI Toolkit has come a long way, and Unreal's UMG can handle complex interfaces. But realistically, both engines are built around rendering pipelines, physics, and 3D scenes. Stripping all of that out to build what is essentially a stylized text application would mean fighting the engine more than using it.

Godot, on the other hand, offers a clean-slate approach to projects. I won't need to disable or exclude any features I don't need — they simply won't be in the project to start with. Its Control node system, native TextEdit and CodeEdit nodes, and lightweight runtime made it a natural fit.

step 2

Building the UI Foundation

First Impressions of Godot

Godot was a genuine surprise; the portability alone was striking. No install, runs without hassle on an underpowered Surface Pro (8GB of RAM!!!) — and doesn't sacrifice capability for it. Their documentation is thorough and well hyperlinked, making it easy to navigate unfamiliar classes and methods. The one real gripe I have is that methods are documented but rarely shown in context, which means a lot of trial and error to understand how things actually behave at runtime rather than just what they theoretically do.

Wrangling the Panel Layout

gif — panel UI showing focus behavior

With six planned panels: Edit, Control, Map, Info, Space*, and Resource; the first task was getting them all sized, positioned, and styled consistently. The design goal was a white rounded-corner outline that turns green when a panel is active. This sounds simple, but I immediately ran into some annoying behavior: PanelContainer doesn't handle StyleBox overrides the same way CodeEdit and TextEdit do. Getting a consistent border effect across node types, each with their own rules about how styles are applied, took manual spoofing of theme behaviors that should have been uniform.

The other small headache was focus management. Clicking off a panel needed to properly clear the active state, but there was no clean way to catch an unfocused click on empty space. The fix was placing a full-screen Button at the back of the scene to absorb any click that didn't land on a panel, forcing a focus reset.

step 3

The Map Matrix

gif — map grid with tooltips

Function vs. Form

The grid is a 4x9 matrix covering areas A1 through D9. Starting at 0 would reduce friction since intuitively you would expect the site number and coordinate to be the same number, but I honestly prefer the matrix starting at 1; I don't know why, it's just more visually appealing to me. The other option is to never use the (n,n) vector format, so there would never be an issue.

update

I have finally decided to fully remove the vector format for querying a location. The matrix will be 1-9.

Column-First Meets Row-First

The first attempt built the matrix and buttons in a single loop iterating column-first, which is the natural way to think about a 2D array. The problem is that GridContainer fills left-to-right row by row, so the buttons end up visually arranged as columns rather than rows — correctly indexed in code, totally wrong layout in UI.

The fix was to abandon efficiency — this will only be done once anyway — and perform two separate passes: populate the matrix column-first, then add buttons in row-major order. Alongside the matrix I built _button_directory, a flat label-to-coordinate dictionary, so button lookups don't require scanning the full array every time.

Making Location Inputs Flexible

The more interesting challenge was find_cell. It is extremely important to me to avoid situations where the player is frustrated because the typing style that is fastest to them doesn't parse correctly. Several different natural ways of expressing a location: the formal [A1], bare A1, a casual a1, or (0,0) as a raw coordinate; I wanted each of these to be valid inputs depending on the player's preference.

Rather than handle each format separately at every call site, I consolidated everything into one function using two regex patterns. The coordinate format is checked first since it's syntactically distinct, and the function returns both the resolved Vector2i and label string together so callers never need a second lookup. Once that was in place, update_map_cell_status and update_map_cell_resource both route through it, meaning format flexibility is inherited automatically everywhere a cell could be referenced.

step 4

The Terminal and File System

Spoofing the Terminal

gif — terminal manipulation

The Control Panel will act as the player's primary interface with the factory itself. The goal was to make a CodeEdit node behave like a real terminal, which turns out to need more intervention than expected. Terminals have a lot of subtle behavioral rules that users take for granted: the caret can't move behind the prompt, clicking doesn't reposition the caret, UP and DOWN scroll through history rather than moving between lines. None of that exists by default in CodeEdit, so each behavior had to be explicitly intercepted and handled.

The history system, command extraction, and input guards all came together quickly enough, but the bigger realization was that complex operations were going to need a way to ask the player follow-up questions mid-command.

Letting the Terminal Request Information

The solution was get_player_input, a function that lets any part of the codebase pause, ask the player something, validate the answer, and resume — without any of that logic pre-existing inside the terminal itself. The caller passes a message, an expected type, a callback, and an optional validator. The terminal switches into AWAITING_CUSTOM_INPUT state, handles all the prompting and re-prompting, then calls the callback with the validated result and emits input_received. Anything that needs to chain multiple questions just pauses for the await signal between calls.

update

This turned out to be one of the more important architectural decisions in the project. Machines use it to ask for missing configuration at startup, the file system uses it to confirm creation and deletion, etc. Without it, all of that would have had to live inside the command handlers rather than in the systems that actually need the information.

Overcoming Arcane Choices

With the terminal functional, the next task was the file system. CodeEdit inside EditPanel handles all file manipulation since it's the node the player directly edits in. Getting syntax highlighting working was the first real fight. Godot exposes a method to retrieve the theme their own editor uses, which would have been perfect — but it isn't callable at runtime. A built-in coding node that can't access the coding theme of the environment it lives in is a baffling decision, but it just meant setting every color up manually by cross-referencing Godot's editor theme values. More tedious than difficult, but the kind of thing that costs time for no satisfying reason.

screenshot — syntax highlighted code in EditPanel (left) vs Godot editor (right)

After that, the file commands themselves came together quickly: load, save, close, create, and delete all wired into the terminal. The EditPanel was also updated at this point; rather than showing a placeholder message when no file is open, it now lists the contents of the custom machines folder, so the panel is always showing something useful.

step 5

Items, Inventories, and Materials

Building the Inventory Handler

Before machines could do anything meaningful, the game needed a solid foundation for moving items around. The design goal was a system flexible enough to be shared across machines, the Vault, and transport ports without needing to be rewritten for each context.

The Inventory class itself is standard: add, take, and several query functions. An issue I want to avoid is a situation where the player sets up a machine but forgot to set a recipe — so even if there is only one possible product, the machine does nothing. So I added two functions: take_max, for situations where you want to drain as much as possible rather than fail on an exact amount, and get_max, which finds the most abundant item. Both will be important later for flexible refining behavior, and hopefully avoid that high-friction situation that bothers me in other sims.

Rethinking the TransPort System

The port system went through one significant design revision. The initial plan was for InputPort and OutputPort to act purely as reference links — each port pointing to its own machine and whatever it was connected to, with the machines themselves handling transfers. The problem with that approach is that machines can have many ports with varying desired behaviors, and centralizing transfer logic on the machine would mean a lot of conditional branching for what should be a uniform operation.

Moving the transfer logic into the ports themselves made each port independently responsible for its own behavior, which is a much cleaner separation. InputPort has a pull() function specifically for pulling from the Vault, since giving the Vault a unique OutputPort for every connected machine would be unnecessary overhead. I created a PortResult that wraps the return so failures report cleanly without crashing.

Setting Up the Vault

Getting the display layout right took the most iteration of anything so far. A plain scrolling list fell apart quickly as the number of resource types grew, so the final solution was a scrollable HFlowContainer that wraps items into columns naturally. The scrollbar styling still needs work, but after far too much fighting with StyleBox, that one got left for later.

One Place for All Materials

The last piece was materials.gd: a static data file that serves as the single authoritative source for every material in the game: ores, raw materials, alloys, synthesized compounds, vaporized gases, and eventually manufactured products. The payoff is that machines never need to hardcode material logic; they query the database and act on whatever they get. Adding a new material type or processing method means changing one file, not hunting through machine scripts.

step 6

Constructing Machines

The Machine Blueprint

With inventories and materials in place, the next step was the machines themselves. The Machine base class is the foundation everything else builds on — it owns the inventory, the input and output ports, the process queue, and the construction requirements. Since the custom machines might have multiple internal machines, I want each loop of the factory to only perform one step at a time. The base class' operate() works through a queue of callables one loop at a time, which means complexity naturally scales with how many processes a machine has registered.

Rethinking Errors

Error handling got its own enum from the start. Every operation a machine performs — adding ports, linking connections, starting up, setting a location — returns a Machine.Error code. Having a consistent language for failures across the whole system meant that when something went wrong during testing it was immediately clear where and why, rather than hunting through print statements.

However, I realized that there needs to be some way to tell what the machines are doing, since you can't literally watch and see what is going in and out of each one. Therefore Machine.Error no longer fits my needs — I need to be able to display the factory's functioning separately from the errors encountered. So I added error codes to the enum definition so that, for example, when a machine is constructed successfully, the error code reads as a success and is given to the operation log rather than the error log.

The Scene Tree is Out to Get Me

This is where things got bumpy. Machines need to check the Vault for construction requirements during construct(), which means accessing resource_panel, a node reference that must be resolved at runtime via @onready. The problem is that @onready variables don't populate until a node is inside the scene tree, and I need to call construct() before add_child(). Every node reference on the machine was null, producing silent failures that were initially very confusing to track down.

The fix was enforcing a strict operation order in machine_manager.gd: instantiate the machine, give it the information it requires, add it to the scene tree first, then call construct(), then call setup(). Making the ordering explicit and consistent across all machine construction paths meant that each step accessed only the data it was ready for.

Preparing for the Future

After setting up the first two specialist classes, I realized that there are multiple machines that might use the same behavior as smeltingFurnace and I could set up a class to streamline later class definitions. refiningMachine serves as a base class for anything that transforms one material into another in a single step. Rather than hardcoding smelting logic into the furnace, refine() takes a process method name and output port, queries Materials for whether the current input can be processed that way, applies the efficiency multiplier, and handles the output. Adding a new type of refining machine later means extending refiningMachine and calling refine() with a different method string, the materials database handles the rest.

The Construction System

gif — construct command walking through steps

With machines proven to work, the construction system needed to give the player a way to build them through the terminal. The construct command kicks off a multi-step flow: type, level, name, and optionally a location for expedition machines. Each step is handled by _collect_construction_data, which advances through a CON_STEP enum and re-prompts for the current step if the player's input doesn't satisfy it.

This layered approach maintains my stance on prompt flexibility. I don't want everything to fall apart if the player left out one piece of the required arguments, it handles what it was given and continues until it has all required information.

Handling Every Outcome

The back end of construction is _continue_construction, which calls machine_manager.add_machine() and routes every possible ConstructionHelper.ERROR result to an appropriate response. Success cases start the machine immediately. Recoverable errors — name already in use, location occupied, insufficient resources — either re-prompt for a different value or drop back to IDLE with an explanation. The goal was that no outcome leaves the player without feedback or stuck in a broken state.

step 7

Making Custom Machines Custom

The Design Goal

screenshot — custom machine config file in EditPanel

The entire point of the Edit Panel is letting players define their own machines. The challenge was designing a system where a plain text config file, written by the player, could create a fully functional machine with sub-machines, port routing, and custom process sequences.

A Major Road-Block and Pivot

Unfortunately — as of writing this — I will not be able to let the player literally program their own machines. Godot does not support any type of compilation during runtime, so I cannot have the player make a file that defines a new class, extending CustomMachine and creating their own functions using other machines. Spoofing the entire GDScript runtime is absurdly out of scope.

Config-Driven Construction

CustomMachine takes a config dictionary and builds itself from it. Sub-machines are instantiated by class reference, inventories are assigned by name so multiple sub-machines can share the same pool, and connections between ports are assigned. The same scene tree ordering problem from before applied here too: sub-machines have to be added to the scene before their ports get assigned, otherwise the @onready references fail in exactly the same way. The construction sequence for a custom machine mirrors the base machine pattern but nested: add parent, construct parent, then for each sub-machine add it, construct it, call setup, assign connections.

Adding a New Blueprint

The last piece was getting player-written files to actually register as machines. A command add_custom_machine in code_edit.gd loads the script file, reads its config dictionary directly off the class, and hands it to machine_manager. With this, the player can write a config, run add [filename], and the machine appears in the construction list, ready to be built with the construct command.
